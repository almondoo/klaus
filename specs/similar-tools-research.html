klaus 類似ツール調査 — 追加すべき機能の検討

調査日: 2026-08-20 / 手法: 5 観点の Web 調査 + 候補ごとの 3 票敵対的検証 / 要約版: similar-tools-research.md

要約

競合 15 ツールとの比較から候補機能 14 件を抽出・検証した。まず着手すべきは次の 3 件で、いずれも実装コスト S、既存の runner・変数解決・ステータスモデルにほぼそのまま乗る。

  1. ステップの retry / poll-until-pass — 非同期 API の検証を可能にする。競合ほぼ全てが保有し、欠落が最も目立つ
  2. --var / --env-file によるアドホック変数注入 — CI からのシークレット注入がワンライナーで完結する
  3. continueOnError — 一括スモークで全体の pass/fail サマリーを取れるようにする

完全棄却された候補は 0 件だが、gRPC ステップ・スクリプティングフック・レポート形式追加の 3 件には反対票が付き、見送りまたは位置づけの修正を推奨する。

調査手法

次の手順で候補を収集・検証した。検証で 2 票以上棄却された候補は推奨から除外する設計としたが、該当は 0 件だった。部分的な反対票は各候補の欄に併記する。

  1. klaus の現状機能をリポジトリ(README / docs / src)から棚卸しし、「不足」判定の基準線とする
  2. 5 観点(YAML シナリオランナー / CLI ファースト HTTP ツール / GUI クライアント / スキーマ駆動テスト / CI・レポーティング)で並列 Web 調査
  3. 候補を横断的に重複統合し 14 件に絞り、各候補の公式ドキュメントを取得して深掘り
  4. 候補ごとに 3 票の敵対的検証: (1) klaus に既存機能・同等物がないか repo を精査、(2) 出典の記述が正確か再取得して照合、(3) klaus のローカルファースト設計・スコープに適合するか

優先度高の推奨機能

実装コストが小さく、実運用上の最頻出ギャップを直接埋める 3 件。3 票検証で反対票なし。

1. ステップの retry / poll-until-passコスト S

どんな機能か
ステップ失敗時に一定間隔で再試行し、成功するか試行回数を使い切るまで繰り返す。Hurl は --retry <NUM>(-1 で無制限)と --retry-interval <MS>(既定 1000ms)の 2 ノブのみで、グローバル(CLI/環境変数)にもステップ単位([Options] セクション)にも設定できる。リトライ対象は HTTP エラー・assert・capture を含む「そのエントリの全失敗」。バックオフや独自条件式は持たず判定は既存 assert をそのまま使い、予算を使い切って初めて非 0 exit になる。
どのツールが持つか
Hurl、Step CI、runn・venom・Karate も同等機能あり。
klaus に加える価値
非同期処理後の結果反映を待つ eventually-consistent なエンドポイントの検証は実 API テストで最頻出のニーズであり、現状の klaus では表現不能。主要競合ほぼ全てが持ち、欠落が最も目立つ。
実装イメージ
step schema に retry: {count, intervalMs} を追加し、runner.ts の既存「リクエスト + assert 実行」をループで包んで固定 sleep を挟む。条件式言語は不要で、既存の exit code 体系(3/4)は最終試行の結果をそのまま使える。

2. アドホック変数注入(--var)と任意パスの環境ファイル(--env-file)コスト S

どんな機能か
Bruno CLI は --env-var NAME=VALUE(複数指定可)でコマンドラインから個別変数を注入・上書きでき、--env-file <path> で collection 外の任意パスの環境定義ファイルを読み込める。ベース環境ファイル → CLI 上書きという 2 層の優先順位が明確。
どのツールが持つか
Bruno CLI、venom。
klaus に加える価値
現状は environments/<name>.yaml の規約配置が必須で、CI からのシークレット注入や一時的な値の差し替えにファイル作成・編集が要る。--var があれば CI ワンライナーで完結し、$protected 環境設計とも整合的に「実行時だけの値」を扱える。
実装イメージ
repeatable な KV フラグのパースと、既存の変数解決順(captures → env file)への 1 層追加(CLI 上書きを env file の上に置く)。--env-file は既存の環境ファイルローダーのパス解決の汎用化で足りる。マスキング対象に含めるかの設計判断は必要。

3. continueOnError(ステップ失敗後も続行)コスト S

どんな機能か
scenarigo はステップに boolean continueOnError を持ち、true ならそのステップの失敗後も後続ステップを実行する。結果は記録され、後続ステップから {{steps.<id>.result == "failed"}} で参照可能。シナリオ中断が伝播しなくなるだけで、新しい出力形式や CLI フラグは不要。
どのツールが持つか
scenarigo。
klaus に加える価値
klaus は初回失敗で残りを skip する固定挙動のため、「独立した複数エンドポイントを一括検証して全体の pass/fail サマリーが欲しい」フローが書けない。CI でのスモーク一括実行と相性が良い。
実装イメージ
step schema に boolean を 1 つ追加し、runner.ts の skipRest 分岐をフラグ時に抑止する。既存の passed/failed/skipped ステータスモデルはそのまま使え、exit code も従来通り失敗があれば 4。

優先度中の推奨機能

フロー表現力・CI 統合を段階的に広げる 5 件。優先度高の 3 件の後に検討する。

4. 条件付きステップ実行(if: 式)コスト M

どんな機能か
runn は runbook レベル / ステップレベルに if: フィールド(expr-lang 式)を置け、vars.*・env.*・steps[n].* 等を参照して false なら失敗ではなく skip(出力上も区別)する。後続ステップは通常実行される。
どのツールが持つか
runn。
klaus に加える価値
「setup が成功しなかったら cleanup を skip する」等の分岐が現状表現不能。continueOnError と組み合わせて初めて「失敗を許容して条件分岐する」フローが完成する。
実装イメージ
主コストは式評価器の導入、または steps.<name>.status == "passed" 程度の限定的な比較構文の自作。skipped 状態は既存モデルにあるため結果の配線は小さい。式言語をどこまで持つかで S にも L にも振れる — 最小構文から始めるのが klaus の宣言的設計に合う。

5. CSV/JSON データファイルによるデータ駆動実行コスト M

どんな機能か
Newman は newman run collection.json -d data.csv で外部データファイルを渡すと、行/オブジェクトごとにコレクション全体を 1 回ずつ実行する。CSV は 1 行目が変数名になり通常のテンプレート {{variableName}} で参照。イテレーションごとの pass/fail が CLI/JSON/JUnit レポートに分かれて出る。
どのツールが持つか
Postman/Newman。Insomnia・Bruno CLI・Hoppscotch・Karate も同等機能あり。
klaus に加える価値
環境ファイルは 1 実行 1 値セット固定のため、同一フローを多数の入力行(ユーザー ID、境界値ペイロード)で回すにはフローファイルを手で複製するしかない。競合のほぼ全てが持つ機能。
実装イメージ
CSV パーサー / JSON 配列ローダー、行ごとの実行 + レポートサイクル展開、既存の変数解決への「イテレーションデータ」層の追加。JSON レポートと history のイテレーション表現の設計判断が必要。

6. タグによる選択実行コスト S

どんな機能か
Bruno CLI(v2.8.0+)は --tags=tag1,tag2(いずれかを持つリクエストのみ実行)と --exclude-tags=...(除外)を組み合わせられる。タグは定義側 meta ブロックの配列で、ランナーは実行前にリストをフィルタするだけ。
どのツールが持つか
Bruno CLI。
klaus に加える価値
「smoke だけ」「write 系だけ」を回すのにフローファイルをサブセットごとに複製する必要がなくなる。CI の段階実行と相性が良い。
実装イメージ
step またはフローの schema に tags: string[] を追加し、run 前のフィルタを 1 段挟む。実行・出力ロジックは無変更。フロー単位かステップ単位かの粒度決定が主な設計判断。なお「除外が包含より優先」の明文記載は出典で未確認(検証時の留保)。

7. フローファイル横断の並列実行コスト M

どんな機能か
Hurl は --test モードでファイルを既定で並列実行し、--jobs N でワーカー数を制御する。ファイル内のリクエストは常に逐次で並列はファイル粒度のみ — 状態・順序のセマンティクスを単純に保つ設計。レポートは入力順に整列して出力される。
どのツールが持つか
Hurl、venom・Karate。Artillery はシナリオ内 parallel: ブロックの別モデル。
klaus に加える価値
大規模 CI スイートで全ファイルの逐次レイテンシを支払わずに済む。フロー内は逐次のままなので capture/変数の既存セマンティクスを壊さない。
実装イメージ
ファイルリストへのワーカープールと、結果の集約・入力順への再整列。klaus はテキスト出力が逐次ストリーミング前提で、history JSONL への追記も並行書き込みになるため、出力の直列化と履歴書き込みの排他が付随コスト。フロー内並列は実行エンジン改修になるため対象外とし、ファイル粒度に限定するのが妥当。

8. レポーター拡張(TAP/HTML 追加・複数同時出力)コスト M

どんな機能か
Newman は -r cli,json,junit のように複数レポーターを 1 実行で併用し、--reporter-<name>-export <path> で個別に出力先を指定できる。Hurl も --report-html / --report-json / --report-junit / --report-tap を 1 実行で併用可能。
どのツールが持つか
Newman、Hurl、Bruno CLI(HTML)、Artillery(HTML)。
klaus に加える価値
人間向け HTML + CI 向け JUnit + ツール向け JSON を 1 実行で出せれば CI 統合の幅が広がる。
実装イメージ
既存の junit.ts / text.ts を「同一 run 結果を購読するレポーターレジストリ」に一般化し、--report junit,tap,... + 形式別出力パスフラグを追加する。TAP は小さく、HTML はテンプレート分のコスト増。
検証時の反対意見: 1 票が「klaus には既に text + JUnit の複数レポーターが存在し、『追加形式がない』という前提は不正確」と棄却。ゼロからの新機能ではなく既存レポーター基盤の拡張として位置づけ直すのが正確な評価。

優先度低の推奨機能

いずれもコスト L で、依存の重さや設計フィットの留保が付く。宣言的機能の拡充後に残るニーズを見てから判断する。

9. モックサーバー(canned レスポンス配信)コスト L

どんな機能か
Karate はモックを Gherkin .feature で書き、pathMatches() / methodIs() / bodyPath() 等のマッチャ式で上から順にルーティングして response / responseStatus / responseDelay でレスポンスを返す。Background の変数が起動中永続するため簡易的なステートフル CRUD 模擬も可能。
どのツールが持つか
Karate、Postman CLI(より浅い実装)。
klaus に加える価値と留保
record/replay は実トラフィックの再生しかできず、未実装 API に対する先行フロー開発ができない。手書きモックはそれを埋めるが、HTTP サーバー常駐 + マッチャ DSL の設計・実装が必要で既存 cassette 機構とは別物。検証でも「実 API 検証という klaus のニッチの外側」とフィット面の留保が付いた。まず replay 側の強化(cassette の手書き許容など)で代替できないか検討する余地がある。

10. OAuth2 トークンフローヘルパーコスト L

どんな機能か
httpYac は Authorization: oauth2 client_credentials のようなヘッダー記法で OAuth2/OIDC を内蔵サポートし、5 フロー(authorization_code + PKCE / implicit / password / client_credentials / device_code)の設定、トークンのキャッシュ・自動更新、RFC 8693 token exchange まで面倒を見る。
どのツールが持つか
httpYac。
klaus に加える価値と留保
現状 OAuth2 保護 API のテストはトークン交換を手動ステップで書く必要があるが、client_credentials フローは「トークン取得ステップ + capture」で今日でも表現できるため緊急度は低い。フル実装は 5 グラント・トークンキャッシュ・ブラウザリダイレクト受信が必要で L。client_credentials 限定の最小版なら M だが既存機能との差が小さい。

11. OpenAPI スキーマ駆動のファズ/適合性テストコスト L

どんな機能か
Schemathesis は OpenAPI 2.0/3.x スキーマから制約認識のプロパティベース入力生成(境界値・型違反)を行い、実 API に発射してスキーマ適合を検証、失敗時は最小再現 + curl コマンド + JUnit XML を出す。Dredd は生成なしの適合性チェックのみ。
どのツールが持つか
Schemathesis、Dredd。
klaus に加える価値と留保
klaus generate の OpenAPI 統合の自然な延長ではあるが、「明示的フローを YAML で定義して実行する」パラダイムに対し生成的ファズは別パラダイムで、事実上の別プロダクト規模。検証でも「スコープ違反ではないが設計フィットが弱い」と明記された。やるなら Dredd 型の適合性チェックのみ(generate 済みフローの assert.bodySchema を spec から自動導出する等)が現実的な縮小版。

12. DB ステップランナー(setup/検証用 SQL)コスト L

どんな機能か
runn は dsn: で DB ランナーを宣言し、ステップ本文の生 SQL を HTTP ステップと同一シナリオ内で実行する。SELECT は rows、更新系は rows_affected / last_insert_id として結果ストアに入り、後続の assert で参照できる。
どのツールが持つか
runn、venom(fixture ロード専用の狭い実装)。
klaus に加える価値と留保
API 呼び出し後の DB 副作用検証・事前データ投入をフローファイル内で完結できる。ただし Node には Go の database/sql 相当の統一抽象がなくドライバごとの個別対応になり、依存軽量を保っている現在の klaus には重い。optional peer dependency 化などの依存設計が必須。

13. ネイティブ gRPC ステップコスト L

どんな機能か
scenarigo は protocol: grpc + target / service / method / message で 4 種の RPC 形状(unary / server-streaming / client-streaming / bidi)を全対応し、proto は .proto ファイル指定または server reflection で取得、HTTP と共通の assert DSL で検証する。
どのツールが持つか
scenarigo、runn。
klaus に加える価値と留保
REST と gRPC が混在するマイクロサービス環境で同一フローファイルに収められる。proto ロード層・全ストリーム型対応クライアント・assert/テンプレートの proto 対応が必要で依存も重い。
検証時の反対意見: 1 票が「docs/dev/requirements.md が gRPC を『任意(当面実装しない)』と明記しており、欠落は意図的なスコープ決定であって競合比較で新たに露呈したギャップではない」と棄却。採用するなら既存のスコープ決定を明示的に覆す判断が先。

14. スクリプティングフック(pre-request / post-response)コスト L

どんな機能か
Bruno はリクエスト/コレクション単位で JavaScript の Pre-Request / Post-Response フックを持ち、req(リクエスト改変)/ res(レスポンス参照)/ bru(変数 get/set、sendRequest、フロー制御)の 3 オブジェクトと chai 風 expect() を提供する。
どのツールが持つか
Bruno、Postman、Insomnia、Hoppscotch、Tavern、scenarigo。
klaus に加える価値と留保
JSONPath/regex に収まらない変換・検証の escape hatch。フル実装は JS サンドボックス・2 フックのライフサイクル・多層変数ストア・req/res ラッパーが必要で L(pre-request 単一フック + vars のみの最小版なら M)。
検証時の反対意見: 1 票が「klaus は JS ランタイム非依存の宣言的 YAML + セキュリティ重視の姿勢であり、JS 実行サンドボックスの追加はローカルファースト・軽依存・純宣言という設計への不適合かつ攻撃面の実質的拡大」と棄却。採用する場合も宣言的機能(retry / if / continueOnError)で埋まらない残余ニーズを見極めてからにすべき。

見送り・保留の整理

3 票敵対的検証で完全棄却(2 票以上)された候補は 0 件。ただし部分的な反対票により、実質的な見送り・位置づけ修正を推奨するのは次の 3 件。

  • ネイティブ gRPC ステップ(候補 13): 要求定義で「当面実装しない」と明記済みの意図的スコープ外。競合比較を理由に自動採用すべきでなく、要求定義の見直しが先
  • スクリプティングフック(候補 14): JS サンドボックス導入は klaus の宣言的・軽依存・セキュリティ重視の設計と衝突し攻撃面を広げる。宣言的機能の拡充で大半のユースケースが埋まる見込み
  • レポート形式追加(候補 8): 「レポーターが JUnit のみ」という前提が不正確。新機能ではなく既存レポーター基盤の拡張として優先度中で扱う

総括

klaus がまず着手すべきは retry/poll-until-pass、--var / --env-file によるアドホック変数注入、continueOnError の 3 点である。いずれも実装コスト S で既存の runner・変数解決・ステータスモデルにほぼそのまま乗り、「非同期 API の検証ができない」「CI からシークレットを注入できない」「一括スモークで全体サマリーが取れない」という実運用上の最頻出ギャップを直接埋める。

その後、if: 条件・データ駆動実行・タグ選択実行という中コスト群でフロー表現力を段階的に広げるのが、宣言的・ローカルファーストという klaus の設計を崩さずに競合との機能差を最短で詰める順路である。
