# localhost UI

`klaus ui` で起動する Web UI。フローの実行(ライブ進捗付き)と履歴の閲覧ができる**ランナー + ビューア**であり、既存のフロー定義の編集はエディタで行う(git-native 思想)。唯一の例外は、記録された履歴から**新しい**フローファイルを作る操作([履歴をフローとして保存](#履歴をフローとして保存))で、既存のフローは UI から編集も上書きもされない。実行・アサーション・履歴のロジックはすべて CLI と同じ `src/core` を使う。

## 起動

```bash
klaus ui [-p <n>] [-H <host>] [--no-open]
```

- 起動するとトークン付き URL(`http://127.0.0.1:<port>/?token=…`)が表示され、ブラウザが自動で開く
- UI アセット(`dist/ui`)が未ビルドの場合は 503 で案内が出る。開発リポジトリでは `pnpm build:all` を先に実行すること(npm インストール版にはビルド済みで同梱される)
- フロー一覧・履歴は**サーバーを起動した cwd** を基準に読まれる。検証したいプロジェクトのルートで起動すること

## 画面

1. **単発 API 実行(デフォルト画面)**: フローを介さず1件のリクエストをその場で実行するタブ。method / URL / ヘッダー / クエリパラメータ / ボディをフォームで編集し、選択中の環境で `{{var}}` を展開して実行する。結果はステータス・所要時間・レスポンスヘッダー・ボディで表示され、レスポンスボディから JSONPath で値を抽出して選択中の環境に保存できる(保存はキー単位のマージで、他のキーは変更しない。保護環境への保存は 403 で拒否される)
2. **フロー一覧(サイドバー)**: cwd 配下のフロー YAML を一覧表示。パースエラーのあるファイルはエラーアイコン + 理由付きで表示され実行不可。フローを選択すると実行ビューに切り替わる。上部の環境セレクタで `--env` 相当の切替、実行ボタンで実行開始
3. **実行ビュー**: ステップが running → pass/fail にライブで遷移(SSE 配信)。「Step n / m」の全体進捗、失敗ステップは自動展開してリクエスト / レスポンス詳細(JSON)を表示、成功ステップはデフォルト折り畳み。完了時にサマリー表示
4. **環境エディタ**: 環境セレクタ横の編集ボタンから開閉し、選択中の環境の key-value をテーブルで編集できる。保存すると YAML 上の既存コメントを保持したまま該当ファイルへ書き戻す。保護環境(`$protected: true` / `readonly`)への保存は 403 で拒否されるため、ファイルを直接編集すること
5. **履歴ブラウザ**: `.klaus/history/*.jsonl` を新しい順に表示。run 単位でグルーピングされ、行クリックでステップ詳細にドリルダウン。フローでのフィルタと「さらに読み込む」ページング。各 run の実行者(`actor`。例: `agent:claude`。agent・CI の実行は強調表示)と環境(`env`)を一覧に表示し、監査項目はステップ詳細にも出る。各 run の行には、別の run との比較とフローとしての保存の操作もある(後述)

## ライブ更新

UI の外で行われた実行(例: ターミナルで AI エージェントが `klaus run` / `klaus req` を実行)は、開いている UI にリロードなしで反映される。

- サーバーが `.klaus/history/` を監視し、`GET /api/history/events`(SSE。他の API と同じ `X-Klaus-Token` 認証)で変更を通知する。通知は連番と変更のあった日付だけを含み、UI は受信後に `GET /api/history` を取り直す
- 履歴一覧はその場で更新され、読み込み済みの件数・スクロール位置・展開中の行は維持される
- 別の画面を表示している間は、履歴ボタンに「新着」バッジが出る。UI 自身から開始した実行では出ない
- ブラウザのタブが非表示の間は接続を切り、戻ったときに再接続して 1 回取り直す。切断された場合はバックオフしながら再接続する
- 同時に購読できるブラウザ接続は最大 16 本

## 実行結果の表示

実行ビューと履歴のステップ詳細には、成功・失敗だけでなく次の情報が表示される。

- **スナップショットアサーション**(`assert.snapshot`): 状態(一致・新規に基準を書き込み・基準を更新・不一致・基準なし)、スナップショットのキーとファイル、不一致のときは差分の一覧(パス・種別・変更前 → 変更後。一覧が打ち切られた場合は総数も表示)。UI からのフロー実行は、`--update-snapshots` なしのローカルの `klaus run` と同じ動作になる。基準がまだ無いステップは基準を記録し(状態は「新規に基準を書き込み」。保護環境では書き込まず「基準なし」になる)、変わった応答で既存の基準が上書きされることはない。
- **OpenAPI の検証**: `klaus.config.yaml` に `run.openapi` を設定していると、`klaus ui` は起動時に一度だけ(`guard`・`http` と同様に。リクエストからは受け付けない)その一覧を読み、UI からのフロー実行のすべての HTTP 応答を仕様に照らして検証する。各アサーションに状態(仕様どおり・仕様に違反・仕様に記載なし・対応するオペレーションなし・検証できず)、照合したオペレーション、違反(位置・パス・メッセージ。表示は最大 10 件で、残りは件数のみ)が表示される。実行後には、照合されなかったオペレーションとどのオペレーションにも対応しなかったリクエストを含むカバレッジの集計が出る。CLI の厳格モードやカバレッジ下限のオプションは UI では使えない。読めない仕様があると、リクエストを 1 件も送らずに実行がエラーになる。
- **警告**: 結果には影響しない警告(例: `http.tls.insecure` による TLS 検証の無効化)は、実行サマリーの上に注意として表示される。
- **リダイレクト**: `http.followRedirects` が有効なとき、ステップ詳細に辿った URL と、別オリジンへ移るたびに落としたヘッダーの名前(値は含まれない)が表示される。
- **スナップショットの集計**: その実行の一致・新規書き込み・更新・不一致・基準なしの件数。変わった応答を実行そのものが基準として受け入れることはない。下の承認で扱う。

## スナップショットの承認

エージェント(または自分)がフローを実行して応答が変わったとき、差分を人間が確認して新しい基準として承認する場所が履歴タブである。

1. 履歴タブで run を開く(行をクリック)。スナップショットの不一致や、基準が無くて書かれなかったものがあれば、「スナップショットの承認待ち」のパネルに、キー・ファイル・差分が 1 件ずつ表示される。run の比較では、新しい方の run(B)の同じパネルがステップ一覧の下に出て、承認待ちのあるステップの見出しには「スナップショットの承認待ち n 件を確認」ボタンがあり、パネルへ移動できる。
2. 1 件なら **この結果を基準として承認**、まとめてなら **すべて承認** を押す。**すべて承認** は、書き込むファイルとキーを一覧で示してから **書き込みを実行** で確定する(**やめる** で取り消し)。
3. 承認すると、その項目に書き込んだファイルと、キーを追加したか置き換えたかが表示される。**承認はリポジトリ内のファイル(`__snapshots__/*.snap.json`)を変更する**ので、`git diff` を確認してコミットすること。

詳細:

- 書き込まれる基準は、run が実行された時点で履歴に保存された(マスク済みの)応答そのもので、[`klaus snapshot accept`](cli.md#klaus-snapshot) と同じ。ファイル内の他のキーは変更せず、作業ディレクトリ内の `__snapshots__/*.snap.json` 以外や、シンボリックリンク経由には書き込まない。
- 承認できるのは、その run の承認待ちとしてサーバーが列挙したものだけ。ブラウザから任意のパスを渡すことはできない。
- 履歴は追記のみのため、承認済みの項目も run を開き直すと一覧に残る。「承認済み」と表示されるのは承認した画面の中だけで、再度承認しても同じ内容が書き直されるだけ。
- **保護環境(`$protected: true` / `readonly`)で実行された run は UI から承認できない**。環境を確認できない run(例: `--env-file` で実行したもの)も同様。UI はエージェントも操作し得る経路で、環境ファイルの編集も保護環境には拒否しているため、保護されたデータ由来の基準は `klaus snapshot accept` でのみ承認する。パネルに理由が表示され、ボタンは無効になる。
- 壊れたスナップショットファイルは 422 で報告され、そのまま残される。先に修正または削除すること。
- 同じステップの他のアサーション(ステータスの検証や OpenAPI 違反など)も失敗している場合、そのスナップショットは承認できない(失敗した応答が基準になってしまうため)。承認ボタンは理由つきで無効になり、**すべて承認** は対象から外して確認画面で知らせ、API は 409 を返す。ステップを直して実行し直すこと。

## run の比較

履歴タブで 2 つの run を選ぶと、その間で何が変わったかを確認できる。たとえば AI エージェントが API に対して行った操作のレビューに使う。

1. run の行で **比較** を押す。2 つ目の run を選ぶよう案内が出る。
2. 別の run の **これと比較** を押すか、案内内の **前回の同じフローと比較** で同じフローの前回の run と比較する(読み込み済みの run の中から探す。見つからないときは先に「さらに読み込む」を押す)。単発リクエストには「前回の同じフロー」が無いため、一覧から 2 つ目を選ぶ。

古い方の run が常に A、新しい方が B になる。パネルにはステップごとに同じ・差分あり・追加・削除が(色だけでなくテキストとアイコンで)表示され、差分のあるステップでは次を示す。

- 結果(状態・HTTP ステータス・エラー、変化があれば所要時間)
- **リクエストの変更**(メソッド・URL・ボディ)。次の項目とは別に表示する
- **レスポンスの変更**(ヘッダー・ボディ・SSE イベント)。パス・種別・変更前 → 変更後の一覧で示す。長い値は「全文を表示」で折りたたまれる。一覧が打ち切られた場合は省略された件数を示し、入れ子が深すぎて比較できない部分木は「深すぎて比較不能」の 1 行で示す

実行のたびに変わる値(id・タイムスタンプ)は除外できる。`$.items[*].createdAt` や `$..updatedAt` のような JSONPath を入力するか、差分から作られた候補のパスをクリックするか、差分の行の「除外」を押す。除外リストを変えると比較をやり直す。既定の揮発するレスポンスヘッダー(`date`・`content-length`・リクエスト ID など)は `klaus diff` と同じく常に除外される。値は履歴に保存された状態のまま表示されるため、シークレットは `***` のままで、シークレット値の変化は見えない。

同じ比較はコマンドラインからも [`klaus diff`](history.md#run-の比較) で使える。

## 履歴をフローとして保存

UI は記録された履歴から**新しい**フローファイルを作れる。[`klaus promote`](history.md#run-のフロー化) と同じ操作で、既存のフローは編集せず、UI からファイルを上書きする手段も無い。

1. run の行で **フローとして保存** を押す。または複数の run のチェックボックスを選び(`klaus req` や単発実行は 1 回ごとに別の run)、**選択した run をフローとして保存** を押す。選んだ run は実行順にステップになる。
2. ダイアログで、アサーションのモード(既定は `schema`)、必要ならベース URL の変数名・フロー名・保存先を指定する。入力に合わせて YAML のプレビューと、その下の確認項目が更新される。
3. 確認項目を見る: 実行前に設定すべき OS 環境変数(履歴ではマスクされていた値)、秘密情報らしいためプレースホルダーに置き換えた値、ステップ間で推論したキャプチャ(つながりを 1 件ずつ確認する)、スキップしたステップ、コミット前に機微な値が残っていないか確認する注意。
4. **保存** を押す。ファイルが書き込まれ、サイドバーのフロー一覧が更新される。

規則と拒否:

- 保存先はカレントディレクトリの中で、拡張子が `.yaml` または `.yml` で、フローが置かれる場所であること。具体的には `api/` または `flows/`(とその配下)、もしくは既にフローファイルがあるディレクトリ(ちょうどそのディレクトリ)に限る。それ以外(たとえば新しいトップレベルのディレクトリ)は拒否される。許可リストにしているのは意図的で、除外ディレクトリ(`environments`・`node_modules`・`.git` など)の拒否リストだと、大文字小文字を区別しないファイルシステムで綴りを変えられる(`Environments/prod.yaml`)と迂回されるため。許可リストにない場所は、フロー探索がスキップするディレクトリにはなり得ない。多層防御として、隠し要素と除外ディレクトリ名は、大文字小文字と Unicode 正規化を揃えて(既存ディレクトリの実際の名前も含めて)拒否する。`klaus.config.yaml` / `.yml` は不可、バックスラッシュを含むパスは不可、シンボリックリンク(宙づりのものを含む)は拒否される。これらは 403 で拒否される。
- 保存先に既にファイルがあれば 409 で拒否される。別の名前かパスにする。
- 記録されたリクエスト値にリテラルの <code v-pre>{{</code> が含まれていると、生成は 422 で拒否され、理由が表示される。klaus はフローの実行時に <code v-pre>{{...}}</code> を展開するため、そのまま保存すると <code v-pre>{{env.X}}</code> のような OS 環境変数が送信先へ送られるおそれがある。CLI には明示的な `--allow-template-literals` があるが、UI には無い。
- 実行可能なステップが無い run(全ステップがスキップ)は保存できない(422)。
- 履歴でマスクされたシークレットは復元されない。<code v-pre>{{env.TODO_*}}</code> のプレースホルダーになるので、OS 環境変数で値を与える。

## 保護環境と送信先ホストの許可リスト

- UI からのフロー実行は `--allow-protected` を渡さないため、保護環境に対しては常に拒否される。単発リクエストは `$protected: true` なら拒否され、`$protected: readonly` なら安全なメソッド(`GET` / `HEAD` / `OPTIONS`)のみ許可される。
- `PUT /api/environments/:name` と「抽出した値を環境へ保存」は、保護環境(`true` / `readonly`)に対して 403 を返す。ファイルを直接編集すること。
- `klaus.config.yaml` に [`guard.allowedHosts`](config.md#送信先ホストの許可リスト-guard-allowedhosts) を設定している場合、UI からの実行・単発リクエストにも同じ判定が適用される。`klaus ui` は起動時に config を読むため、リストを変更したら再起動すること。
- `klaus.config.yaml` に [`http`](config.md#http-クライアント-http)(リダイレクト追従・cookie・proxy・TLS)を設定している場合、UI からの実行・単発リクエストにも使われる。許可リストと同じく起動時に一度だけ読み、リクエストからは受け付けない。
- UI からのフロー実行が保護環境のために拒否された場合、メッセージは「`klaus ui` は保護を上書きできない」ことと `klaus run --allow-protected` を案内する。履歴に記録される拒否理由は汎用の文言のまま。
- UI からの実行は履歴に `actor.kind: human` で記録される([実行履歴](history.md#監査項目)を参照)。

## セキュリティモデル

ローカル専用の設計であり、**リバースプロキシ等で外部公開してはならない**。

| 対策 | 内容 |
|---|---|
| バインド | 既定は 127.0.0.1。`-H`/`--host`(または `klaus.config.yaml` の `ui.host`)で変更可能 |
| 認証トークン | 起動時に `crypto.randomBytes(32)` で生成。比較はタイミングセーフ |
| 初回アクセス | `GET /?token=…` の検証成功で `klaus_token` Cookie(SameSite=Strict / HttpOnly)を発行 |
| API 認証 | 全 `/api/*` で `X-Klaus-Token` ヘッダー必須(不一致 401) |
| CSRF | POST/PUT/DELETE はさらに Cookie 一致 + `Origin` ヘッダーが存在する場合は同一オリジンのみ許可 |
| DNS rebinding | 全リクエストで `Host` が `127.0.0.1:<port>` / `localhost:<port>` 以外なら 403(`--host` に非ループバックアドレスを明示指定した場合は、ポート一致のみの検証に緩和) |
| CORS | ヘッダーを一切付けない(同一オリジン配信のみ) |
| path traversal | ファイルパスを受ける API・静的配信で cwd / dist/ui 外への解決を 403 で拒否 |

上記の認証トークンは、起動時に stdout へ表示されるだけでなく、ブラウザ自動起動コマンド(`open` / `xdg-open` / `cmd /c start`)の引数としても渡される。共有のマルチユーザーホストでは、この引数が他のローカルユーザーからプロセス一覧(`ps` や `/proc/<pid>/cmdline`)経由で読める可能性がある。該当する環境では `--no-open` を指定してブラウザの自動起動を避け、表示された URL を自分で開くこと。詳細は [SECURITY.md](https://github.com/almondoo/klaus/blob/main/SECURITY.md) を参照。

HTTP API の仕様と内部構成は [../dev/ui-api.md](https://github.com/almondoo/klaus/blob/main/docs/dev/ui-api.md) を参照。
