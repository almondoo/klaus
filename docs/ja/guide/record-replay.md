# record / replay モード

`klaus run` に `--record <dir>` または `--replay <dir>` を渡すと、HTTP リクエスト/レスポンスをファイル(カセット)経由でやり取りするモードになる。ネットワークが遮断されたサンドボックス内での検証や、破壊的な API(決済・送信系など)を毎回実際には叩かずに検証したい場合に使う。

- **record モード(`--record <dir>`)**: 実際にリクエストを送信しつつ、レスポンスを secrets でマスクしたうえで `<dir>` のカセットファイルに追記する。
- **replay モード(`--replay <dir>`)**: ネットワークへは一切出ず、`<dir>` のカセットから応答を再生する。

`--record` と `--replay` は同時指定できない(両方指定すると stderr にメッセージを出して exit code 1 になり、何も実行されない)。

## カセット形式

カセットは `<dir>/cassette.jsonl`(単一ファイルの JSON Lines)に固定される。1行 = 1リクエスト分のレスポンスで、スキーマは次のとおり(`v: 1`)。

```jsonc
{
  "v": 1,
  "method": "GET",              // 大文字化した HTTP メソッド
  "url": "http://…",            // レンダリング済み URL(マスク済み)
  "status": 200,
  "headers": { … },
  "bodyText": "…"                // レスポンス本文の生テキスト
}
```

- `url` は record 時点で secrets によりマスクされたうえで保存されるため、平文のシークレットはカセットファイルに残らない。マスク規則は[実行履歴](history.md)や `--report junit` と同じ(<code v-pre>{{env.X}}</code> で解決した値と、その URL エンコード形・form-urlencoded 形・JSON エスケープ形が対象)。
- `bodyText` も同様にマスクしてから保存する。
- `headers`(レスポンスヘッダー)も含め、エントリ全体に同じマスク処理(maskDeep)を適用するため、レスポンスヘッダーに含まれるシークレットも同様にマスクされる。
- replay 時は `bodyText` の Content-Type が `application/json` を含む場合のみ JSON としてパースし直す(それ以外はテキストのまま返す)。パースに失敗した場合もテキストのままフォールバックする。

## マッチング規則

replay 時は、実行中のステップの **method + マスク済み URL の完全一致** で、カセット中のエントリを検索する。

- record と replay は**同じ env / secrets** で行うことを前提にしている(URL のマスクは実行時に判明している secrets を使ってから比較するため、record と replay で解決される secrets が異なると一致しなくなる)。
- カセットに同一キー(method + URL)の行が複数あっても、**先に記録された行**が採用される。同じキーへの複数回のリクエストは常に同じ応答を返す(非消費型。呼び出し順で使い切られたりはしない)。
- カセットに一致するエントリが無いリクエストは、明確なエラーとしてステップが `error` になり、CLI の exit code は **3** になる。エラーメッセージには一致しなかったキー(マスク済み)と、`--record <dir>` で再記録する案内が含まれる。
- `--replay` 指定時にカセットファイル自体が読み込めない(存在しない・壊れている等)場合も、実際に最初の HTTP ステップが実行されたタイミングで同じ exit code 3 のエラーになる。

## SSE / WebSocket ステップは非対応

`--record` / `--replay` 指定時、SSE(Accept: text/event-stream または `sse` ブロックを持つステップ)や WebSocket(`ws` ブロックを持つステップ)が含まれるフローを実行すると、そのステップは明示的な `error` になる。黙って実ネットワークへ素通しすることはない。record/replay の対象は HTTP ステップのみ(GraphQL over HTTP を含む)。

## 実行履歴・その他出力への影響

record/replay モードでも、`.klaus/history/*.jsonl` への書き込みは(`--no-history` を付けない限り)従来どおり行われる。stdout の text/JSON 出力、`--report junit`、secrets のマスキング(`--no-mask`)といった他のオプションの挙動もモードの有無に関わらず変わらない。

## ユースケース

- **ネットワークを遮断したサンドボックスでの検証**: CI やエージェント実行環境がネットワークにアクセスできない場合でも、事前にローカルや別環境で record したカセットを使って `--replay` すれば、リクエスト/アサーションのロジックを検証できる。
- **破壊的な API の再実行防止**: 決済・メール送信・リソース削除など、実行のたびに副作用を伴う API を検証したい場合、一度だけ record し、以降は `--replay` で同じ応答を使い回すことで、副作用を伴う呼び出しを最小限に抑えられる。

## モックサーバー

`klaus mock <dir>` は、`<dir>/cassette.jsonl` に記録した応答を返すローカル HTTP サーバーを起動する。別のクライアント(フロントエンド、スクリプト、他のツール)が実際の API の代わりに `localhost` と通信できる。ネットワークへは一切転送しない。

```bash
klaus run api/create-user.yaml --record ./cassettes
klaus mock ./cassettes --port 4885
# klaus mock started: http://127.0.0.1:4885
curl http://127.0.0.1:4885/users/1
```

待ち受け URL は stdout に、リクエストごとのログは stderr に出力される。Ctrl+C(SIGINT / SIGTERM)で停止し、exit code 0 で終了する。それ以外の終了コードは、カセットが存在しない・不正・空の場合、または `--origin` に該当する記録が無い場合が **2**、不正なオプション値(`--port 99999` や形式の誤った `--origin` など)・ポート使用中・その他の実行時エラーが **1**。

| オプション | 説明 |
|---|---|
| `-p, --port <n>` | 待ち受けポート。既定は `4885`(UI は 4884)。`0` で空きポートを自動選択 |
| `-H, --host <host>` | バインド先アドレス。既定は `127.0.0.1`。外部からの接続を許可するには `0.0.0.0` を明示する |
| `--cors` | 寛容な CORS ヘッダーを付け、preflight(`Access-Control-Request-Method` 付きの `OPTIONS`)に応答する。既定はオフ |
| `--delay <ms>` | すべての応答に固定の遅延を加える |
| `--ignore-query` | method と path のみで照合する |
| `--sequence` | 同じリクエストの複数の記録を記録順に返し、尽きたら最後を繰り返す |
| `--origin <url>` | 指定したオリジン(例: `http://api.example.com`)で記録されたエントリだけを返す |
| `--allow-host <host>` | この `Host` ヘッダー名(ポートなし)も許可する(複数指定可)。Host 検証を緩めるため、下記を参照 |
| `--json` | 起動行(stdout)とリクエストログ(stderr)を JSON Lines で出力する |

### Host ヘッダーの検証

DNS リバインディング(別サイトのページが自身のホスト名をあなたのマシンに向け直し、ブラウザ経由で記録済みの応答を読み取る攻撃)を防ぐため、mock は想定外の `Host` ヘッダーを持つリクエストを、照合の前に `403`(小さな JSON ボディ付き)で拒否する。

- ループバックアドレスにバインドしている場合(既定): `127.0.0.1:<port>`・`localhost:<port>`・`[::1]:<port>` だけを許可する(大文字小文字は区別しない)。`<port>` は実際の待ち受けポートで、`--port 0` でも同様。`Host` が無いリクエストは拒否する。
- ループバック以外にバインドしている場合(`--host 0.0.0.0` など): ホスト名を事前に決められないため、ポートの一致だけを確認する。
- `--allow-host <host>` は、待ち受けポート付きで許可するホスト名(例: docker-compose のサービス名)を追加する。指定するたびに検証が緩むため、自分が管理する名前だけを指定する。
- `--cors` はこの検証を緩めない。

### モックのマッチング規則

mock は **method + path + query** で照合する。クライアントは localhost に向かうため、記録時のホストは使わない(URL 全体で照合する replay とは異なる)。

- query 文字列はまず完全一致で比較し、一致しなければ query パラメータの順序を問わず比較し直す。
- 同じキーの記録が複数ある場合は、常に最初の1件を返す(replay と同じ)。`--sequence` 指定時は記録順に返し、最後の1件を繰り返す。
- カセットに複数のオリジンが含まれる場合はすべて統合する。複数のオリジンが同じ method + path + query を記録していたときは、カセット内で先に現れたものを採用し、衝突の一覧を警告として起動時に表示する。1つに絞るには `--origin` を使う。
- リクエストターゲットはパスとして解釈する。`//host/path` の先頭を host とは扱わず、absolute-form(`GET http://host/path`)はその path と query を使い、それ以外の形式(`*`、`CONNECT`)は `400` / `405` で拒否する。
- どれにも一致しないリクエストには、小さな JSON ボディ(`error`・`method`・`path`・近い記録済みパス `closest`。記録済みボディは含めない)付きの `404` を返し、ログを1行出力する。

### モックの応答

記録した status・ヘッダー・ボディを保存されたまま返す。`content-length` は再計算し、再送出すると不正になるヘッダー(`transfer-encoding`・`content-encoding`・`connection`・`keep-alive` などのホップバイホップヘッダー)は落とす。ボディを持たない応答は HTTP の規則に従う。記録された 1xx・204・304 はボディも `content-length` も付けずに返し、`HEAD` リクエストにはヘッダー(対応する GET と同じ `content-length`)だけを返してボディは返さない。記録された `access-control-*` ヘッダーは、記録元オリジンの CORS ポリシーが mock には当てはまらないため常に落とす。`--cors` 指定時は mock 自身の寛容なヘッダーを付ける。record 時にシークレットがマスクされているため、記録済みのボディやヘッダー内のシークレットは `***` のまま返り、mock が元の値に戻すことはない。

## 使用例

```bash
# 1. 実際にリクエストを送りながらカセットを記録する
klaus run api/create-user.yaml --record ./cassettes

# 2. 以降はネットワークに出ずに同じ検証を再生する
klaus run api/create-user.yaml --replay ./cassettes
```
