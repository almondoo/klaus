# klaus 改善提案

klaus を実装・検証したセッションを踏まえた改善提案。**このセッション中に実際に起きた事象**を根拠にしている（推測ベースの一般論は含めない）。各項目に「やる価値があるか」の判定と概算コストを付ける。

判定の凡例: **推奨** = 実施すべき / **条件付き** = 特定の運用になったら / **見送り** = コストが便益を上回る。

---

## A. 製品（klaus 本体）の改善

### A-1. `pnpm build` が `dist/ui` を破壊する — 対応済み（2026-08-08）

**根拠**: このセッションで**2回**踏んだ。`tsup.config.ts` の1つ目のエントリが `clean: true` で `dist/` 全体を消すため、`pnpm build`（および内部で build を呼ぶ `pnpm test`）を実行すると Vite が出力した `dist/ui` が消える。結果 `klaus ui` が 503「静的ファイルが見つかりません」になる。

利用者にも同じことが起きる：`pnpm build` は自然な操作なのに、その後 `klaus ui` が壊れる。ドキュメントの注意書き（`VERIFICATION.md`・`docs/dev/architecture.md`）で回避しているが、**ドキュメントで回避する設計そのものが誤り**。

**修正案**（いずれか）:
1. `tsup.config.ts` の `clean` を全エントリ `false` にし、`"clean": "rimraf dist"` 相当を別スクリプト化して `build:all` の先頭でのみ実行する
2. UI の出力先を `dist/ui` から独立ディレクトリ（例: `ui-dist/`）に変え、`resolveStaticDir()` をそちらに向ける。`files` に追加

**採用した対応**: `tsup.config.ts` の `clean` を `false` にした。当初 1 のグロブ指定（`clean: ["dist/*.js", ...]`）を試したが、**tsup は配列を渡しても outDir 全体を削除する**ことが実測で判明したため（`dist/ui` の中身が全消失し空ディレクトリだけ残った）、無効化に切り替えた。tsup の出力（`index.js` / `cli.js` / `server.js` とマップ・型定義）は毎回上書きされるため、clean 無しでも成果物は正しく更新される。

ただしこれだけでは、エントリを削除・リネームした際に古い成果物が `dist/` に残り、`files: ["dist"]` 経由で publish に同梱される**別のリスク**が生まれる（セキュリティレビューで指摘）。そこで `scripts/clean.mjs` を追加し、**リリース用の `build:all` は clean → build → build:ui** の順で走るようにした。開発時の `pnpm build` 単体は clean しないので `dist/ui` は保持される。

検証済み: (1) `pnpm build` 単体・`pnpm test`（内部で build を呼ぶ）の後でも `dist/ui/index.html` が生存すること、(2) `dist/` に古いファイルを仕込んで `build:all` を実行すると除去され、かつ `dist/ui` が正しく再生成されること。`VERIFICATION.md` と `docs/dev/architecture.md` の回避用注意書きは削除した。

### A-2. SSE の受信イベントが履歴に残らない — 対応済み(2026-08-08)

**根拠**: `src/core/runner.ts` の SSE 分岐は `responseSnapshot.body = undefined` とし、`events` は `StepResult` にしか入らない。一方 WebSocket は受信メッセージを `response.body` に配列で記録している。**同じ「ストリーム受信」なのに永続化の扱いが非対称**で、UI の履歴ブラウザからは SSE の受信内容が一切見えない。

履歴スキーマは additive 変更なら `v: 1` のままでよい契約なので、`HistoryEntry` に `events?: SseEvent[]` を足すだけで済む。

**コスト**: 1時間程度（runner の記録・型・UI 表示・テスト）。**判定: 推奨** — SSE 検証は要件で「既製ツールに無い差別化機能」と位置づけているのに、その結果が履歴に残らないのは機能として不完全。

**対応**: `HistoryEntry` に `events?: SseEvent[]` を追加し、SSE ステップで受信したイベントを履歴に記録するようにした(`response.body` は従来どおり undefined のまま)。UI の履歴ブラウザでも events を展開表示する。詳細は [history.md](../guide/history.md)。

### A-3. skipped ステップが履歴に残らない — 対応済み(2026-08-08)

**根拠**: `runner.ts` の skip 分岐は `historySink` を呼ばないため、履歴 JSONL に skipped 行が存在しない。UI の履歴から「どこで止まって、以降が流れなかったか」が追えない（失敗ステップは残るので推測はできる）。

`HistoryEntry` に `status` フィールドが無い点も併せて設計変更になる（現状は assertions の内容から成否を推測している）。

**コスト**: 2〜3時間（スキーマ拡張 + UI のグルーピング表示ロジック修正 + テスト）。**判定: 条件付き** — 履歴 UI を実際に多用するようになってから。失敗行が残る以上、情報の欠落は限定的。

**対応**: `HistoryEntry` に `status?: "passed" | "failed" | "skipped"` を追加し、skipped ステップも `status: "skipped"`・request/response なし・assertions 空の行として履歴に記録するようにした。`status` を持たない旧エントリは従来どおり assertions から導出するフォールバックで読み込み互換を保つ。詳細は [history.md](../guide/history.md)。

### A-4. シークレットが履歴に平文で残る — 対応済み(2026-08-08)

**根拠**: 履歴は**テンプレート解決済みの値**を記録するため、<code v-pre>{{env.TEST_PASSWORD}}</code> で渡した値が `.klaus/history/*.jsonl` に平文で残る。`docs/guide/history.md` に注意書きを書き、`.gitignore` にも入れてあるが、**`klaus ui` の履歴ブラウザは同じ内容をブラウザに表示する**。

**修正案**: フロー定義でマスク対象を宣言（`request.secretFields: ["password"]`）、または `Authorization` / `*token*` / `*password*` といったヘッダー名・キー名ベースの自動マスク。

**コスト**: 3〜4時間（マスク層の設計・core への組み込み・UI 表示・テスト）。**判定: 条件付き** — 個人のローカル検証に留める限りは現状の注意書きで足りる。チームで履歴を共有する運用に入るなら必須。

**対応**: 修正案とは異なる方式を採用。<code v-pre>{{env.X}}</code> で OS 環境変数から解決した値(長さ 4 文字以上)を履歴エントリへの書き込み直前に `***` へ自動置換する(`maskHistoryEntry`)。request の url/headers/body、response の headers/body、SSE events の data が対象。デフォルトのファイル sink・カスタム sink の両方に適用され、ライブ実行結果(UI の実行ビュー)や environments ファイル由来の値はマスク対象外。境界の詳細は [SECURITY.md](https://github.com/almondoo/klaus/blob/main/SECURITY.md) と [history.md](../guide/history.md) を参照。

### A-5. `environments/` の解決が cwd 基準のみ — 対応済み(2026-08-08)

**根拠**: `resolveEnvironmentPath(cwd, name)` は実行時カレントディレクトリ基準。このセッションでも、サンプルを動かすのに `cd examples` が必須になった。プロジェクトのサブディレクトリから `klaus run api/foo.yaml` を叩くと環境ファイルが見つからない。

**修正案**: cwd から上方向に `environments/` を探索（`.git` かファイルシステムルートで打ち切り）、または `--env-dir <path>` オプション。前者は「どこから叩いても動く」体験になるが、探索範囲の上限を明示する必要がある（path traversal 修正と同じく境界を持たせる）。

**コスト**: 1〜2時間。**判定: 推奨** — CLI の初回体験に直接効く。ただし探索仕様は明文化すること。

**対応**: 前者(上方探索)を採用。`resolveEnvironmentPath` が cwd から親ディレクトリへ順に辿り、`.git` を含む祖先ディレクトリ(そのディレクトリ自身は含めて調べる)またはファイルシステムルートで打ち切る。各候補ディレクトリで path traversal の境界チェックを行ってからファイルシステムへアクセスする。

### A-6. `klaus init` が無い — 対応済み(2026-08-08)

**根拠**: 新規プロジェクトで使い始めるとき、`environments/local.yaml` とサンプルフローを手で作る必要がある。このセッションでも `examples/` を人手で作成した。`klaus init` で雛形を吐けば初回体験が短縮される。

**コスト**: 1〜2時間。**判定: 条件付き** — 他人に配布する（npm 公開する）段階で価値が出る。自分だけで使う間は `examples/` をコピーすれば足りる。

**対応**: `klaus init` サブコマンドを追加した(`src/cli/init.ts`)。

### A-8. モバイルドロワーのフォーカス管理 — 見送り（現時点）

**根拠**: ブラウザ QA で確認。767px 以下のドロワーを開いても**フォーカスがドロワー内に移らず**、背後のハンバーガーボタンに残る。閉じるボタンには前方 Tab では到達できず Shift+Tab が必要。オーバーレイ UI の一般的な作法（開いたら中にフォーカスを移し、閉じたら開いた要素に戻す、開いている間はフォーカスを閉じ込める）を満たしていない。

**判定: 見送り** — 正しく直すならフォーカストラップ + フォーカス復帰が必要で、手書きするか Radix の Dialog/Sheet に置き換えるかの判断を伴う（コスト 2〜3時間）。一方、この UI は **768px 未満でしか現れないドロワー**であり、対象は「ローカル開発ツールを狭い画面でキーボード操作するユーザー」という稀な組み合わせ。Escape での close は対応済みで最低限の脱出手段はある。モバイル幅での利用が実際に発生したら Radix Sheet への置き換えで対応する。

### A-7. 複数フローの並列実行 — 見送り（現時点）

**根拠**: `runFlows` は順次実行。独立したフローが多いと総時間が線形に伸びる。

**判定: 見送り** — 現状の想定規模（ローカル API の数フロー）では体感差が出ない。並列化すると出力の逐次性・履歴の順序・レートリミットへの配慮が必要になり、複雑性の増加が便益を上回る。フロー数が増えて実測で問題が出てから。

## B. プロセス（私の進め方）の改善

このセッションで**実際に起きた失敗**とその教訓。同種の作業を再度行うときの申し送り。

### B-1. 自分が書いた注意書きを、自分の手順に反映していなかった

`docs/dev/architecture.md` に「`build:all` の順序が必須（tsup の clean が dist/ui を消す）」と自分で書きながら、その後の検証で `pnpm test` を実行した後に UI を起動して 503 を出した。**しかも2回**。

**教訓**: ドキュメントに書いた制約は、自分の実行手順にもチェックとして組み込む。より根本的には A-1 のとおり**ドキュメントで回避している設計は直す**。

### B-2. サブエージェントの失敗を見切るのが遅かった

ドキュメント作成でサブエージェントが**5回**ストール／API エラーで落ちた（大きな単一タスク → 分割 → それでも失敗）。3回目でようやく「自分で直接書く」に切り替えたが、**2回目の時点で切り替えるべき**だった。

**教訓**: 同一タスクで2回失敗したら、分割ではなく実行主体の変更（主モデルが直接やる）を検討する。特に「調査は完了していて、あとは書くだけ」の状態なら主モデルが書いた方が速い。

### B-3. 自動テストと多レンズレビューを通過した後に、手動 E2E で実バグが2件出た

`VERIFICATION.md` の手順を一通り実行した結果、**アサーション期待値のテンプレート未展開**（<code v-pre>equals: "{{testEmail}}"</code> が文字列のまま比較されていた）と**日付依存テスト**が発覚した。それまでに 118 テスト・正しさ／簡素化／テスト過不足／セキュリティの4レンズレビューを通過していたにも関わらず。

**教訓**:
- テンプレート展開のような「**仕様の網羅マトリクス**」（どの場所で展開が効くか）は、表形式で全組み合わせをテストする。個別のふるまいテストでは抜けが見えない
- 実際にコマンドを叩く E2E 検証は、自動テストの代替にはならないが**自動テストも E2E の代替にならない**。両方必要

### B-4. 時間依存のテストを書いた

履歴テストが `new Date("2026-08-07")` をハードコードしており、日付が変わった翌日に落ちた。

**教訓**: 日付・時刻に依存するテストは、固定値を書くなら**プロダクション側にも同じ固定値を注入できる形**にする（`appendHistory(dir, entry, date)` のように）か、テスト側で「実行時点の日付」を使う。

### B-5. 防御を追加したとき、同種の入力を横展開で確認しなかった

セキュリティレビューで見つかった `POST /api/runs` の `env` path traversal は、**同じリクエストボディの `path` には境界チェックが入っていた**。防御を1箇所に入れた時点で「同じ経路の他のパラメータはどうか」を横展開していれば、レビューを待たずに防げた。

**教訓**: 入力検証・境界チェックを追加したら、**同じ信頼境界を通る他の入力を必ず洗い出す**。1つ直したら周辺を見る。

### B-6. 良かった点（維持する）

- **多レンズの並行レビュー**（正しさ／簡素化／テスト過不足／セキュリティ）は機能した。特に「テストの過不足」レンズは、不足6件だけでなく**検出力ゼロの重複テスト1件の削除**も指摘し、テストの水増しを防いだ
- **確信度80以上のみ報告**の制約により、レビュー結果の三角測量（複数レンズが同じ根本原因を別角度で指摘）が成立した。SSE の `response.body` 二重保持は、簡素化レンズとテスト過不足レンズの両方から指摘され、同一原因だと分かった
- **再現スクリプト付きの検証**を要求したことで、SSE 切断フリーズと WS ソケットリークが「理論上の懸念」ではなく**実証済みバグ**として確定した

## 優先順位（提案）

| 順 | 項目 | 理由 |
|---|---|---|
| 1 | A-1 ビルドの clean 問題 | 利用者が確実に踏む。コスト最小 |
| 2 | A-2 SSE の履歴記録 | 差別化機能の結果が残らないのは機能の不完全 |
| 3 | A-5 environments の探索 | 初回体験に直結 |
| 4 | A-4 シークレットのマスク | 履歴を共有する運用に入る前に |
| 5 | A-3 / A-6 | 実際の利用頻度を見てから |

A-7（並列実行）は現時点では**実施しない**ことを推奨する。
